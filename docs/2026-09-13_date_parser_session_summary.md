# 오늘 작업 요약 (date_parser 최종 점검)

담당: 이수민
브랜치: `claude/itda-ocr-github-integration-wpblqh`
관련 커밋: `3e3f4f4`, `e802faa`

이 문서는 오늘 date_parser(날짜 파싱 모듈)에서 한 작업을 팀원들이 코드를 안 봐도
이해할 수 있게 정리한 거예요. "date_parser"는 OCR이 읽어낸 텍스트 조각들
(예: "소비기한", "2026.07.15") 중에서 어떤 게 진짜 소비기한 날짜인지 찾아서
`연/월/일` 형태로 정리해주는 부분이에요.

## 1. 오늘 고친 것 4가지

### ① 소비기한이 유통기한보다 항상 이겨야 하는데 안 그랬던 문제

한 제품 사진에 소비기한 날짜와 유통기한 날짜가 둘 다 찍혀 있으면, **소비기한이
항상 정답**이어야 해요 (대회 공식 규칙). 그런데 기존 코드는 "소비기한이든
유통기한이든 그냥 아무 날짜 관련 단어"로 취급해서, 어쩌다 유통기한 글자가
날짜 숫자에 더 가까이 있으면 유통기한 쪽을 정답으로 골라버리는 경우가 있었어요.

**고친 내용**: 소비기한/사용기한을 "무조건 이기는 키워드"로 따로 분리했어요.
추가로 수민님이 요청한 대로, "날짜가 소비기한 글자에 우연히 더 가까운데 사실은
더 이른 날짜라서 틀린 경우"에는 **더 나중 날짜를 우선**하도록 로직을 추가했어요.

### ② "4월 31일" 같은 존재하지 않는 날짜를 그냥 통과시키던 문제

4월은 30일까지만 있는데, OCR이 "04월 31일"처럼 잘못 읽은 경우 기존 코드는
이걸 그대로 정답으로 내보냈어요. 이제는 "이 달에 이 날짜가 있을 수 있는지"를
연도 없이도 미리 걸러내서, 31일은 버리고 "2026년 4월, 일은 모름(NONE)" 으로
처리해요. (2월 29일은 윤년이 있을 수 있으니까 그대로 허용돼요.)

### ③ 캐스케이드(재시도) 노트북에서 이미지 1개가 억울하게 틀리던 버그

`validation_recheck_300_cascade.ipynb`에서, 512px로 먼저 OCR을 돌려보고
날짜를 못 찾으면 회전→고해상도→CLAHE 순서로 재시도하는 구조예요. 그런데
"날짜를 찾았다"고 판단하는 기준이 첫 단계(512px)에서만 느슨하게 되어 있어서,
글자가 살짝 깨진 경우("202.6,01.07") 실제로는 못 읽었는데도 "찾았다"고
착각하고 재시도를 멈춰버리는 이미지가 1장(729번) 있었어요. 이제 모든 단계에서
같은 엄격한 기준을 쓰도록 통일해서, 이 이미지가 정상적으로 고해상도 단계까지
가서 정답(2026-01-07)을 찾도록 고쳤어요. 다른 299장에는 영향 없음을 실제
데이터로 확인했어요.

### ④ (정선우님 피드백 반영) "월+연도만 있는 날짜"를 아예 못 읽던 문제

정선우님이 전달해주신 피드백에서, 부분적으로만 읽히는 날짜(일부 정보가 NONE인
경우)의 정확도가 유독 낮다는 지적이 있었어요 (18건 중 4건만 정답, 22%).

원인을 찾아보니: "2023년 5월" 같이 **일(day) 없이 월+연도만 있는 날짜**를
읽을 때, 연도가 항상 앞에 와야만("2023.05") 인식이 됐고, "월이 먼저
오거나"("05/2023") "쉼표로 구분되면"("2023,05") 아예 못 읽고 있었어요.
실제 실패 사진들 중에 "EXP 02/2023", "EXP:01,2022" 같은 케이스가 정확히
이 문제였어요. 두 경우를 추가로 인식하도록 고쳤어요.

**일부러 안 고친 부분**: "12/22"처럼 연도가 2자리이고 다른 확실한 단서가
전혀 없는 경우는, 무작정 다 받아주면 무게(1.5g)나 비율 같은 관련 없는 숫자를
날짜로 잘못 인식할 위험이 커서 이번엔 손대지 않았어요. 정선우님이 말씀하신
"안전한 수정만" 기준에 맞춘 판단이에요.

## 2. 검증 방법 (얼마나 믿을 만한지)

- 유닛 테스트 87개 전부 통과 (오늘 새로 추가한 테스트 6개 포함)
- 실제 정답이었던 205장 사진으로 재확인 → **회귀(있던 정답이 틀려짐) 0건**
- 실제 오답이었던 사진들로 재확인 → **새로 정답이 된 것 17건, 새로 틀려진 것 0건**

즉 "새로 뭔가 고쳤다가 다른 게 망가지는" 일은 실측 데이터 기준으로는
없었다는 뜻이에요.
